# OpenRemoteConnector MVP：让 Agent 按你的规则使用已有设备

版本：0.5；更新及调研日期：2026-10-18。状态：产品验证与交付提案，尚未实现、部署或通过验收。

依据：[PRD v0.4](PRD.md)；架构约束见 [职责与行为契约](ARCHITECTURE.md)。本文将需求收敛为价值假设、首版工作流、交付范围和验证方法，不新增技术栈决策。需求冲突以 PRD 为准；全部 P0 发布要求继续有效。旧版已归档至 [2026-10-15 MVP](history/MVP-2026-10-15.md)。

## 1 Most Value Point

### 1.1 核心价值

> **让你选择的 Agent，通过一个自建入口使用已有的多台设备；每个 Agent 能用哪台设备、在哪种环境执行、何时需要确认，最终由设备所有者决定。**

这里的 **Most Value Point** 指最值得验证的用户价值；下文 **MVP** 指 Minimum Viable Product，即最小可用产品。两者不混用。

首版聚焦一个具体问题：开发者已经有工作站、家庭服务器或 VPS，也已选择自己的 Agent，却需要重复接入设备、交付过宽权限，或为了隔离任务重新准备整套环境。ORC 希望减少这笔成本，同时让用户明确选择两条执行路径：

- **复用真实环境**：已信任的任务使用指定账户的现有文件、工具和依赖，按所有者选择自动执行、规则过滤或逐次确认。
- **控制试验范围**：需要隔离的任务使用获准副本与已验证工具环境，修改先形成差异，再由所有者决定是否回写。

两条路径共享目标选择、授权、任务查询和撤销体验；权限不因换设备、换客户端或环境故障而自动扩大。宿主执行仍受执行账户真实权限约束，不能承诺与隔离模式等价的保护。

### 1.2 调研后的判断

**统一 MCP、多设备、自托管、远程命令和异步任务都已有开源方案。ORC 当前没有已证实的独占功能或市场壁垒。** Remote Agent Gateway 与 WebCodex 尤其接近当前 PRD，必须作为实际替代方案，而非只拿相邻产品作比较。[Remote Agent Gateway][S1]、[WebCodex][S2]

最值得验证的是一个组合体验：**按客户端与设备分别授权，由终端落实当前策略，在同一使用流程中明确选择宿主或隔离执行，并准确呈现任务与撤销结果。** 这是基于公开资料提出的产品假设，尚不能宣称其他项目均不支持，也不能宣称 ORC 已经更安全或更轻量。

| 待验证价值 | 用户为什么可能在意 | ORC 必须拿出的证据 |
| --- | --- | --- |
| 权限由设备所有者决定 | 信任同一个入口，不意味着所有 Agent 都能访问所有设备 | 客户端 A、B 权限不同；新增设备不继承授权；终端拒绝越权请求；用户能正确解释授权范围 |
| 按任务选择执行边界 | 既需要现成工具链，也需要处理不宜直接写宿主的任务 | 两种环境完成真实任务；六种环境/策略组合可解释、可验收；隔离不可用不转宿主 |
| 接入和维护成本可接受 | 用户不愿为管理连接再维护一套复杂平台 | 非作者完成分角色安装、实际客户端接入及第二台设备登记；记录全部必要步骤与费用 |
| 任务和收权结果可信 | 换会话后想查原任务；撤销后想知道究竟停没停 | 普通请求断开后可查原任务；重试不重复启动；失联撤销显示停止待确认；恢复先同步权限 |

单个功能容易被复用。若组合体验经验证有价值，后续积累应是稳定的设备能力契约、客户端兼容记录、权限与故障回归案例，以及持续降低接入成本的安装体验。

## 2 开源替代方案与定位

### 2.1 调研方法与结论边界

通过公开搜索发现候选，再读取项目维护方的 README、架构、安全说明、安装说明和许可证。下表覆盖直接竞品及相邻替代方案，来源固定到调研时的提交，见 §10。未安装或实测这些项目，未执行性能、安全审计或成本基准测试。

“文档明确”表示维护方有相应说明，不代表本次验证通过；“未确认”不能解读为不存在。开发分支、技术预览、已发布版本与停止维护的源码分别标明，不把规划能力算作稳定交付。

| 项目及关系 | 公开资料明确说明的能力 | 与 ORC 的重叠、可替代范围 | 对 MVP 的影响 |
| --- | --- | --- | --- |
| [Remote Agent Gateway][S1]，直接竞品 | 自托管单 MCP 网关；远端主动出站；稳定设备身份；Shell/工作区契约；命令拦截、文件哈希校验与版本状态；标为 Technical Preview | 已覆盖“一个入口连接多设备、无需终端公网入站”的核心拓扑；说明命令策略位于网关，Shell 使用系统账户权限 | 把它作为最接近的基础连接对照；重点实测终端本机策略、分客户端授权、隔离回写和异步恢复能否形成值得迁移的增益 |
| [WebCodex][S2]，直接竞品 | Server/Runner；真实机器的项目、Git、工具链；异步 Jobs；本地策略与访问控制；架构说明支持 Runner 出站连接与任务对账 [架构][S2A] | “复用自己的开发环境、集中接入、任务超出单次请求”均已重叠；不能再将其描述成仅提供本地 provider 的工具 | 编码工作流必须与其正面对照；ORC 聚焦设备授权和两种执行环境，避免扩成完整项目/会话平台 |
| [YawLabs/ssh-mcp][S3]，轻量替代 | 复用 SSH 配置、密钥与跳板；命令、文件和多主机操作；命令正则策略，并说明其适用范围 | 已有 SSH 网络与权限配置的用户可能几乎不需要额外终端组件 | ORC 必须证明新装执行端值得；单纯封装远程 Shell 不足以成立 |
| [Desktop Commander MCP][S4]，本机能力替代 | 文件、进程、长命令与安装入口；README 提供远程 MCP 服务入口；安全说明区分护栏与 OS 隔离 [安全模型][S4A] | 本机文件/命令自动化已有成熟工具形态；其远程服务的部署、开源范围及多设备能力本次未确认 | 不能把“能操作本机”或“能从云端调用”当差异；需要说明授权与执行环境的完整使用成本 |
| [MCPHub][S5]，网关替代 | 自托管聚合本地/远程 MCP；稳定端点、认证、分用户凭据、访问可见性、日志与健康检查 | 统一入口、集中认证及工具治理已有直接替代；设备执行契约并非本次资料确认的重点 | 不重做通用 MCP 聚合、工具市场或智能路由；把终端执行体验作为交付重心 |
| [E2B][S6] / [E2B Embed][S6A]，隔离执行替代 | 沙箱、命令与文件 SDK；Embed 文档提供自有 Linux 单机部署、无需 E2B 账号的路径，并声明硬件虚拟化等条件 | 用户只需要运行不可信代码时，应把它纳入选型；不能以“它只能托管云端、不能自建”作为 ORC 优势 | 不竞争通用弹性沙箱基础设施；验证“已有宿主工具链 + 可选隔离”是否是用户实际需求 |
| [Daytona 公开仓库][S7]，历史相邻方案 | README 描述沙箱、快照、进程与 MCP 等能力，同时声明 2026-06 核心开发转入私有代码库，公开仓库不再维护 | 可参考其执行环境产品形态；本次不把其商业服务等同于仍持续维护的完整开源方案 | 选组件前核实维护与分发条件；不能按过去印象直接列为首版基础依赖 |

WebCodex 的 `main` 包含开发中的安装方案，维护方明确记录原生安装和端到端验收未全部完成；比较安装体验时必须固定可获得的版本，不能把文档中的目标流程记成实测结果。[版本与安全说明][S2S]、[安装验收状态][S2V]

### 2.2 哪些卖点不足以成立

- “开源、自托管、没有强制官方账号”：多项方案已具备，是目标用户的选择条件。
- “一个 MCP 管多台设备、终端只需出站”：Remote Agent Gateway 与 WebCodex 已明确覆盖相近路径。[来源][S1]、[来源][S2A]
- “运行远程命令、读取文件、返回任务结果”：SSH 类和本机工具类项目已有大量重叠能力。[来源][S3]、[来源][S4]
- “有沙箱”：已有专门基础设施；有价值与否取决于受支持工作流、边界、依赖准备和使用成本。[来源][S6A]
- “一个 Skill / 一条安装命令”：分发入口可以简化体验，仍须计算认证、网络、角色、权限和维护步骤。

ORC 不以无中继、每设备独立 MCP、强制隔离或指定运行时作为卖点；这些旧约束已由 PRD 取代。自建 MCP 是用户选择并信任的处理节点，终端不必直接暴露给 Agent。

### 2.3 什么时候直接用已有项目

已有 SSH 且只需要受信任的远程命令，先评估 SSH 类 MCP；主要需求是完整远程编码与项目工作流，先评估 WebCodex；只需要出站设备接入与标准 Shell/文件能力，先评估 Remote Agent Gateway；只需要隔离代码执行，先评估 E2B。上述是依据公开定位的初筛，最终取决于固定版本的实测。

M0 先做“配置已有项目、为其贡献扩展、独立实现”的比较。只有安装、授权或两种执行环境工作流存在真实且反复出现的缺口，才有理由投入独立产品；不把竞品文档没有写到某功能作为必须重写的证据。

## 3 首批用户与验证任务

### 3.1 用户范围

首批用户是拥有至少两台 Linux 设备、已经使用编码或通用 Agent 的个人开发者。同一所有者管理 MCP 和终端，能通过 CLI 或已有 SSH 完成管理。优先招募有重复任务的用户，而非只想演示远程执行的用户。

典型配置是一台 Ubuntu 工作站和一台 VPS/家庭服务器，使用 Codex CLI，并具备 ChatGPT 自定义远程 MCP 的相应账户权限。只有一台本机设备的用户仍受支持，但不足以单独验证多设备价值。

单纯本机 Shell、临时云端沙箱、团队权限、设备运维平台和交互式远程桌面不是首批定位。Agent 已有的本机工具权限不受 ORC 约束。

### 3.2 必须跑通的工作流

| 工作流 | 用户操作与任务 | 验证的价值 | 可观察结果 |
| --- | --- | --- | --- |
| W1 复用已有环境 | 授权 Agent 在设备 A 的指定账户执行已有测试或构建命令；选择宿主自动执行或规则模式 | 不迁移项目、不重建工具链即可使用真实设备 | 使用实际账户、目录和声明环境；无需逐条批准已自动放行请求；命令退出和输出可辨认 |
| W2 先隔离再回写 | 为设备 B 批准文本项目快照，Agent 修改副本、运行已包含依赖的离线测试、生成文本报告 | 可在明确范围内试验并审阅修改 | 宿主批准前不变；差异绑定基线；冲突不覆盖；产物有界可读；缺依赖不联网或转宿主 |
| W3 增加设备与更换入口客户端 | 为已有 MCP 新增第二台终端；分别为 Codex CLI、ChatGPT 授权 | 设备接入与 Agent 授权分离，复用统一入口 | 已接入客户端不逐设备重配 MCP；新设备初始不开放；两个客户端权限可不同；结果始终标明设备 |
| W4 查原任务并收回访问 | 提交任务后结束请求或重连同一主体；随后撤销授权，并模拟终端失联 | 任务可持续查询，收权反馈可据实判断 | 查回原任务而非再次启动；新操作及结果读取受阻；实际停止、待确认、失败和未知不混淆 |

四项都应使用专用目录和人工测试数据。W1 不以任意工具链均受支持为前提；W2 必须随发布包给出可重复的官方样例；W3 不以两条连接共用同一个可冒用主体代替身份验收。

## 4 MVP 交付边界

### 4.1 三部分产品

```mermaid
flowchart LR
    A[Agent 与一个 Skill 入口] --> M[用户选择的独立 MCP 服务]
    M --> L[本机终端执行端]
    M --> R[远程终端执行端]
    L --> LP[本机授权与执行策略]
    R --> RP[本机授权与执行策略]
```

图表达产品职责，不预先指定协议、进程数或通信方向。仅出站终端接入可达 MCP 是必须验证的场景。

| 部分 | 首版交付 | 不承担的职责 |
| --- | --- | --- |
| Agent Plugin / Skill | 连接指引、设备选择、任务与结果查询、拒绝/审批/离线处理；优先复用宿主原生 MCP | 保存长期秘密、授予权限或替所有者批准；不另装 ORC 常驻客户端 |
| 独立 MCP 服务 | 客户端认证、设备目录、按授权呈现能力、路由任务、查询结果；可与执行端同机或异机部署 | 安装后自动控制所在主机、扩大终端许可、冒充目标终端环境 |
| 终端执行端 | 信任确认、本机授权、两种环境和三种策略、任务管理、文件/产物、撤销与停止结果 | 自动信任新 MCP、自动转宿主、默认提权或继承其他设备授权 |

### 4.2 支持矩阵

以下均为交付目标，尚无实测兼容声明。

| 维度 | P0：Linux 首版必须具备 | P1 / 后续 |
| --- | --- | --- |
| MCP 与终端系统 | Ubuntu 24.04 LTS x86_64；至少两台独立 Linux 设备 | Apple Silicon macOS 优先；其余组合逐项验证 |
| Agent | Codex CLI；具有相应权限的 ChatGPT 远程 MCP 路径 | Claude Code 首先验证互操作性，再按需求扩展其他宿主 |
| 部署 | 同机、集中、混合；一个 MCP 同时连接本机及远程执行端 | 同一终端多 MCP、跨服务级联和故障转移另评估 |
| 网络 | 同机、已有互通网络、终端只出站且有可达 MCP、声明的云端路径 | 自动打洞、额外连接服务分别定义，不作为 P0 前提 |
| 执行 | 隔离/宿主 × 自动执行/规则过滤/逐次确认，共六种组合 | 更多执行环境、细化策略按真实任务扩展 |
| 安装管理 | Linux 单命令进入三种角色向导；CLI/已有 SSH 可安装、审批、撤销、诊断、升级卸载；Agent 一个 Skill 入口 | macOS 签名、公证 App，分别验收休眠与后台生命周期 |

不把本地 MCP、远程 MCP 与客户端产品线的协议声明推定为 ORC 兼容；发布记录实际版本、认证方式、网络路径、执行组合和测试日期。

### 4.3 两种执行环境与三种策略

| 执行环境 | 自动执行 | 规则过滤 | 逐次确认 |
| --- | --- | --- | --- |
| 隔离 | 在批准副本与环境限制内直接运行；回写另需确认 | 通过确定性规则后运行；回写另需确认 | 批准具体任务后运行；回写仍单独确认 |
| 宿主 | 按明确授权在真实账户执行，不追加命令过滤或逐条审批 | 按配置字段允许、拒绝或转审批；可直接产生真实副作用 | 批准具体任务后执行；审批不保证预览全部副作用 |

初始无执行权限。授权必须绑定实际客户端主体、MCP 来源、终端、账户、环境、动作、策略及期限。扩大范围、降低限制或更换 MCP 须重新确认；隔离权限不覆盖宿主权限。

规则只匹配 PRD §5.3 声明的确定性字段，至少支持精确匹配和显式不限制；拒绝优先于转审批，再优先于允许。无匹配默认拒绝，可由所有者改为转审批；未知字段、不可解析内容和发生变化的上下文不猜测放行。不实现自然语言安全判定或任意脚本行为分析。

宿主工作目录与命令规则不构成文件隔离。开放任意命令后，任务可使用执行账户的实际文件和网络权限，也可能影响同账户的 ORC 状态；不能承诺完全追回派生进程或撤销已有副作用。

### 4.4 最小任务、文件与管理能力

| 能力 | 首版范围 |
| --- | --- |
| 目标与发现 | 仅显示获准设备及能力；稳定 ID 路由；每次请求和结果明确设备、账户、环境与策略；离线不换目标 |
| 命令 | 区分程序及字面参数列表、指定解释器脚本；固定目录、账户和允许的环境；无静默账户回退或跨调用隐式 Shell 状态 |
| 任务 | 非交互、有截止时间；有界预提交输入；接受后返回独立标识；可查询、取消并读取有限输出；区分退出、失败、超时、停止与未知 |
| 文件与产物 | 隔离使用已批准快照，默认排除凭据配置、版本控制元数据、链接及特殊文件；文本修改、离线测试、文本产物均有完整样例 |
| 审批 | 本地所有者入口管理；绑定具体请求、脚本入口内容与当前策略；单次消费；内容改变、过期或撤销后失效；Agent 不能自批 |
| 写入 | 隔离回写检查差异与基线，冲突和部分失败逐项报告；宿主按当前放行策略直接修改，不强加第二次差异审批 |
| 生命周期 | 请求结束不取消任务；控制链路失联按配置处理，默认停止，可选继续至原截止时间且不超过授权期；显式取消/撤销/到期始终优先 |
| 恢复 | 同一次提交重试关联原任务，不静默重跑；重连先同步撤销及策略并对账；无法证明执行与否时返回未知 |
| 记录 | 两端记录可关联的主体、目标、动作、环境、策略与结果；默认不记秘密、完整参数和正文；输出转义、限量、可清理 |
| 维护 | MCP 与执行端独立停止、升级和卸载；未知必需限制拒绝；升级处理在途任务；回退不恢复撤销、已消费批准或历史执行 |

资源上限、失联检测、输出保留等数值在 M0 测量并于发布前冻结，按环境说明哪些是硬限制。首版不指定语言、框架、认证产品、数据库、连接协议实现或沙箱后端。

### 4.5 明确不做

P0 不包含内置模型、聊天/记忆系统、完整 IDE 或项目协作平台、交互式 PTY 与既有会话接管、远程桌面、团队 RBAC、多租户、第三方 MCP 自动安装或聚合市场、跨 MCP 级联、自动云资源购买、强制官方账号或默认公共中继。

不承诺任意网络零配置互通、任意工具链/GPU/原生应用即装即用，或系统管理操作的正式适配。Linux 首版无需桌面 UI；第三方 provider、Windows、WSL2、NAS、边缘和移动终端均不作为 P0 执行设备。

## 5 首次成功体验与成本

1. **先检查条件**：选择同机或已有服务器部署，分别检查 Agent→MCP、终端→MCP 所需可达条件；说明域名、证书、服务器或连接服务的准备步骤与费用承担者。
2. **按角色安装**：一个 Linux 命令进入“仅 MCP”“仅执行端”“完整安装”向导。仅安装宿主模式所需能力时，不强制准备隔离依赖；首次无执行权限。
3. **建立信任**：所有者核对 MCP 和设备身份，登记终端。配对不等于向任何客户端开放执行。
4. **配置第一项授权**：选择客户端、目标、账户、环境、范围、放行策略和期限；隔离路径另审阅输入清单。
5. **接入实际 Agent**：通过一个 Skill 进入原生连接与认证流程；保留客户端必需的原生设置。实际客户端完成无副作用能力查询后，才显示该路径已验证。
6. **完成第一项任务**：在明确设备运行 W1 或 W2，看到目标、状态与结果。查询连通、执行授权和任务成功分别标记。
7. **添加第二台设备**：只增加执行端及相应授权；Agent 已有 MCP 入口保持有效，不能自动获得新设备权限。验证其仅出站连接路径。
8. **结束与收权**：结束请求后查询原任务，再显式取消或撤销；展示访问受阻与实际停止的分别结果。

分别记录设备安装、MCP 准备、网络准备、客户端接入、首次授权和任务完成时间；另记第二台设备及第二个客户端的增量成本。首轮真实体验计入下载、必需人工配置和中断；复测可单列已满足网络前提后的时间，不能只宣传后者。

没有可达 MCP 且设备均只出站时，安装器早期解释缺失条件，允许只装本地组件，不报告远程成功。ChatGPT 路径必须从实际调用环境验证，不能用用户浏览器或 MCP 本机自检替代。

## 7 交付顺序与继续投入条件

阶段沿用 PRD 的 M0—M5；以下补充每阶段应回答的产品问题，不承诺工期。

| 阶段 | 最小交付与验证 | 出口条件 |
| --- | --- | --- |
| M0 价值与可行性 | 用固定版本评估 Remote Agent Gateway、WebCodex 和适合用户现状的轻量替代；验证三部分职责、真实 Agent 认证与主体委托、出站终端、任务持续查询、去重、撤销及隔离正向工作流 | 给出可复验证据、条件和成本；确认哪些缺口需要 ORC；比较扩展已有项目与独立实现；通过后再写具体技术决策 |
| M1 同机闭环 | MCP 与本机执行端保持独立；授权、两类环境/三种策略、任务、结果和撤销 | 仅 MCP 无执行权；六种组合和本地管理成立，不能只实现宿主路径就称完整 MVP |
| M2 多设备闭环 | 在已有入口增加独立远程 Linux；覆盖集中与混合部署 | W1—W4 跨设备成立；新增设备不重配 Agent、不继承权限；出站、失联恢复和正确路由通过 |

## 8 如何判断 Most Value Point 是否成立

### 8.1 试用设计

计划邀请 5–10 位目标用户试用两周，沿用 PRD 建议。优先覆盖已有 SSH 的用户、需要云端 Agent 访问出站终端的用户，以及同时有宿主与隔离任务的用户。样本用于发现重复工作流与阻塞原因，不能推导市场规模或统计显著性。

每人先说明当前做法并选择一个真实重复任务，再评估最适合的现有方案。比较任务、设备、账户权限、网络、工具和输入数据保持可比；分开记录首次安装和后续重复执行。只有两者都实际跑过才给出时间或步骤差值，未跑通则记录原因，不编造“节省百分比”。

Remote Agent Gateway 与 WebCodex 至少各有一组适合其定位的实测对照；已有 SSH 用户另比较 SSH 类 MCP。安装由谁协助、固定版本、额外服务器/服务、失败及人工补救步骤均计入记录。

### 8.2 指标与记录口径

| 指标 | 记录方法 | 为什么有用 |
| --- | --- | --- |
| 首次真实任务完成 | 完成 W1 或 W2 的人数/尝试人数；记录分阶段耗时与失败原因 | 判断用户是否能从安装走到有价值结果 |
| 第二台设备的增量成本 | 从新增设备开始，到已有 Agent 完成该设备获准任务；记录新增组件、配置和确认次数 | 验证统一入口是否减少实际维护负担 |
| 权限理解 | 用户独立说明谁能用哪台设备、执行账户、环境、审批条件和撤销状态；与实际配置核对 | 判断安全选择是否可理解，不能只看工具成功率 |
| 重复使用 | 两周中用户主动发起任务的不同日期、重复的工作流及未再使用原因；排除作者安排的演示 | 验证持续需求，避免连接成功即算留存 |
| 两种环境的选择 | 按任务记录选择原因、是否受阻、是否能用现有方案更轻松完成 | 判断可选隔离带来的收益是否值得增加成本 |
| 任务与撤销可信度 | 原任务查询、重试、失联撤销等场景的实际状态与用户理解；产品错误单列 | 检查用户能否依赖结果做后续操作 |
| 替代方案差值 | 可比任务的时间、步骤、维护负担及用户选择理由；同时记录优势与劣势 | 判断独立产品是否优于配置或扩展现有项目 |

本版不虚构已有基线，也不将任意数值写成发布承诺。M0 先取得基线，再在 M4 开始前固定试用判断阈值、分母及退出用户处理方式；不得看完结果后移动标准。连接数、调用数、GitHub stars 与“愿意试试”不单独算价值成立。

### 8.3 决策规则

- **继续投入**：多个用户主动重复同类工作流；能正确理解授权与环境；相比合适替代方案，出现可复现的配置、维护或权限管理收益，且用户愿意继续承担新增执行端的成本。
- **调整重点**：需求主要集中在一种环境、一个客户端或已有工具的缺口。先改进工作流或考虑上游贡献；若拟删减当前 P0，另行修订 PRD，不能在实现中静默缩减。
- **停止扩张、优先复用**：用户主要使用一次性远程 Shell；现有方案配置后已满足需求；ORC 增加的授权、环境及维护成本大于收益，或收益只能靠放宽权限实现。

“没有已证实差异”是允许出现的调研结论。不能为了维持立项把普遍能力重新命名成独有卖点。

## 9 待验证风险

| 风险 | 下一步要取得的证据 |
| --- | --- |
| 直接竞品功能继续接近 | 每次阶段决策复核固定版本；以实际任务比较，不沿用本次快照判断永久缺口 |
| P0 跨两种环境、六种组合及两类客户端，范围仍然较大 | M0 明确共同契约与复用边界；保持阶段交付，正式发布不绕过 PRD 门槛 |
| 用户不愿新增执行端或运维 MCP | 记录现有 SSH/网关方案成本和真实额外步骤；不能假设“一个安装命令”消除运维 |
| 隔离环境难以完成用户项目 | 用官方离线样例证明正向可用，再记录真实依赖差距；不以宿主回退掩盖失败 |
| 宿主授权过宽、用户误解边界 | 按执行账户展示真实影响范围；验证理解与收权状态；不把规则宣传成沙箱 |
| 云端入口、账号或受限网络阻塞 | 从实际 Agent 环境验证两段链路；记录前提及费用；未满足条件早期失败 |
| 撤销、故障和升级只实现了表面状态 | 对照 AC-11/12/16/19/28—30 保留实际证据；停止请求与终止确认分开；恢复不扩权、不重放 |
